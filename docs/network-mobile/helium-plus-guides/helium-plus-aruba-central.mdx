## Prerequisites

Before starting, confirm the following:

- Aruba system is running AOS 8.10.x.x or later
- Network uses an on-prem Aruba Mobility Controller
- APs are adopted and serving traffic
- Existing SSIDs are functional
- Aruba infrastructure has outbound internet access to Helium AAA endpoints

---

## High-Level Steps

1. Upload Helium RadSec Certificates
2. Configure SSID for RadSec
3. Configure Passpoint Settings
4. Connect and Validate

---

:::note

This guide applies to "Classic Central".  
If your Aruba dashboard shows a "Classic Central" toggle, enable it.

:::

## Upload Helium RadSec Certificates

Helium requires RADIUS traffic to be secured using RadSec (RADIUS over TLS).

Download the following from the Helium onboarding process (either from the WiFi Conversion process
or sent to you by your Helium Plus contact):

- RadSec Server CA (ca.pem)
- RadSec Client Certificate (combine cert.pem and key.pem into a single PEM file; for example:
  `cat cert.pem key.pem > client_combined.pem`)

Navigate to:

**Global → Organization → Network Structure → Certificates**

### SSID General Configuration

Set the following values:

- Under 'General', set the SSID name to 'Helium'.

Click **Next**.

- Configure VLAN and IP assignment as required for your deployment

Click **Next**.

- Under Security, set Security Level to Enterprise
- Set Key Management to WPA3-Enterprise

Click **Add** next to **Primary Server** and create a new authentication server.

---

### Create RadSec Authentication Server

Configure the authentication server with the following values:

- Server Name: `Helium-RadSec`
- Server Type: RADIUS
- Enable RadSec: enabled
- IP Address: radius-bf.wifi.hellohelium.com
- RadSec Port: 2083
- RadSec Keepalive Type: TCP Keepalive

Click **OK**.

## Standalone Mobility Controller (Without Central)

If the Mobility Controller is managed from its own web UI (`https://<controller-ip>:4343`) instead
of Aruba Central, the steps above still apply, with these differences. Verified on an Aruba 7005
running AOS 8.10.0.16.

### Upload Certificates in the Controller UI

Navigate to **Configuration → System → Certificates → Import Certificates** and add:

- RadSec Server CA (`ca.pem`): Type `TrustedCA`, Format `PEM`
- Combined client certificate and key: Type `ServerCert`, Format `PEM`

Deploy the pending changes. Note the names you give each certificate; you need them in the next
step.

### Enable RadSec from the CLI

Uploading the certificates in the web UI only stores them on the controller. The
`radsec-trusted-cacert-name` and `radsec-client-cert` lines below attach them to the RadSec server;
without them, both certificate fields show `N/A` and the TLS connection to Helium cannot start.

The RADIUS server form in the controller's web UI has no RadSec or certificate fields, and the web
UI has no CLI console. Enable RadSec over SSH (`ssh admin@<controller-ip>`) or the console port:

```
configure terminal
aaa authentication-server radius Helium-RadSec
  host radius-bf.wifi.hellohelium.com
  enable-radsec
  radsec-port 2083
  radsec-trusted-cacert-name <ca-cert-name>
  radsec-client-cert <client-cert-name>
  nas-identifier <your-nas-id>
  key radsec
exit
aaa server-group <your-server-group>
  auth-server Helium-RadSec position 1
exit
write memory
```

- Enter the server lines while the prompt shows `(RADIUS Server "Helium-RadSec")`. Commands entered
  at the `(config)` prompt are rejected.
- The client certificate keyword is `radsec-client-cert`. `radsec-client-cert-name` is not accepted.
- `enable-radsec` warns that a trusted certificate is required until `radsec-trusted-cacert-name` is
  set. This is expected.
- If the WLAN was created with the WLAN wizard, the server group is named `<ssid>_dot1_svg`.
- Idle SSH sessions time out after a few minutes. If you see `*** IDLE TIMEOUT ***`, reconnect
  before pasting commands.

Verify the configuration:

```
show aaa authentication-server radius Helium-RadSec
```

A working configuration looks like this (example output from an Aruba 7005 on AOS 8.10.0.16; your
NAS ID and certificate names will differ):

Check these lines:

**Diagnostics → Logs** for repeated `Failed to open TLS socket for server Helium-RadSec` errors;
once the connection is established they stop.

### Check the Controller IP

On a controller that was previously configured for another network, confirm that **Configuration →
System → General → Controller IP address** is on a VLAN that both your APs and the internet can
reach. If it is not, APs can discover the controller but stay `Down`, and RadSec traffic cannot
reach Helium. Changing the controller IP requires a reboot.

Also confirm that the VLAN assigned to the Helium WLAN gives clients a routable address with
internet access.

## Troubleshooting

If authentication fails, check the following:

- Certificates: verify the Server CA and the combined client certificate were uploaded correctly and
  assigned to the device.
- Network: ensure outbound TCP 2083 to the Helium RadSec endpoint is allowed from your Aruba
  infrastructure.
- Logs: check Aruba controller logs and the Helium RADIUS logs for Access-Request / Access-Accept
  messages.
- RadSec connection: on a standalone controller, go to **Diagnostics → Logs**.
  `TCP connect to server Helium-RadSec failed` means the controller cannot reach Helium on TCP 2083.
  If TCP connects but TLS still fails, recheck the CA and client certificate names on the server.
- Certificate import fails with `Certificate is not yet valid`: the controller clock is behind the
  certificate's start date. Check **Configuration → System → General → Clock**; if it uses NTP, make
  sure an NTP server is listed, then deploy and re-import.
